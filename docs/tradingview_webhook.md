# TradingView webhook · 30m

Адрес: `https://broke.smautomator.cloud/api/webhooks/tradingview?key=<TRADINGVIEW_WEBHOOK_KEY>`.
Ключ хранится только в `.env` сервера; в git его не добавлять. Сгенерировать новый:
`python -c "import secrets; print(secrets.token_urlsafe(32))"`.
После изменения ключа пересоздать API: `docker compose up -d --no-deps api`.

На обычном графике **30 минут**, в Scalping_SMA включить **Dynamic alert() messages**,
создать alert с Condition **Any alert() function call** и указать адрес в Webhook URL.
Используется обычный индикатор, а не диагностическая intrabar-копия.
Текст формирует сам Pine; вручную заменять его JSON не требуется.
TradingView требует включённую двухфакторную аутентификацию для webhook;
см. [официальную инструкцию](https://www.tradingview.com/support/solutions/43000529348-how-to-configure-webhook-alerts/).

API отвечает `201` только после commit в БД. При неверном ключе — `401`, при
отсутствующем ключе в окружении — `503`, при пустом/не-UTF-8 теле или распознанном
TF, отличном от 30 — `422`, свыше 64 KiB — `413`. Сопоставление parity не выполняется
в обработчике webhook. Неизвестные форматы сохраняются с `parse_status=unparsed`
для дальнейшего анализа. Хранятся исходное тело, SHA-256, время получения UTC,
распознанный инструмент, сигнал, направление и метрики. `.P` в символе снимается
при сопоставлении с движком; биржа сохраняется.

Таблица `tradingview_alerts` добавлена миграцией `0006`. API удаляет до 10 000
записей старше **30 суток от получения** при запуске и каждый час; при большой
очереди следующие циклы продолжают очистку. Это отдельная политика, она действует
и при `RETENTION_MODE=preview`. Локальные engine signals/checkpoints не удаляются.
GET API показывает только последние 30 суток. Время получения не подменяет время свечи.
Одинаковые сообщения сохраняются отдельно: без timestamp/event ID нельзя достоверно
отличить повторную доставку от одинакового сигнала на следующей свече.

- `/api/tradingview/alerts?limit=100&offset=0&symbol=ETHFIUSDT` — исходные сообщения с пагинацией.
- `/api/parity/tradingview?limit=100` — сопоставление последних сообщений с локальными signals.
- **Alerts** — последние входящие webhook; **Parity** — результаты сопоставления.

Обычный Pine-текст не содержит время свечи и идентификатор настроек. Поэтому
`TIME_CANDIDATE` ищет тот же сигнал, направление, биржу, символ и TF в окне ±90 секунд
от доставки; `NO_TIME_CANDIDATE` означает отсутствие такого кандидата, а не доказанное
расхождение движков. Отчёт пересчитывается при чтении и учитывает поздние локальные данные.
Показываются необработанные разности метрик; TradingView округляет их в сообщении.
Для будущего источника с точным временем поддержан JSON-конверт:
`{"message":"<native dynamic alert text>","bar_start":1790553600000}`.
`bar_start` — начало свечи UTC в миллисекундах, кратное 1 800 000.
Тогда `SIGNAL_MATCH`/`SIGNAL_NOT_FOUND` сравнивают наличие сигнала на указанной свече.
Это не проверяет идентичность настроек, отсутствие лишних локальных сигналов или полную
последовательность intrabar; общий статус остаётся `UNVERIFIED`.

Ключ не включается в ответы/записи БД. Nginx не пишет access log для webhook,
а Uvicorn удаляет query string из access log этого маршрута. При включении логов
дополнительного внешнего proxy его redaction нужно настроить отдельно.

## Файлы правил Alerts

«Сохранить правила в файл» выгружает все **сохранённые** правила в JSON:
`{"format":"brokeweb-alert-rules","version":1,"rules":[...]}`.
Несохранённый черновик редактора в экспорт не входит. ID, версия, журнал доставки
и состояние подавления повторов не переносятся.

«Импортировать из файла» добавляет новые правила с новыми ID и версией 1, не
перезаписывая существующие. Сохраняет ON/OFF, условия, шаблон, режим, частоту и cooldown.
Весь файл проверяется до единой транзакции: ошибка одного правила отменяет весь импорт.
Лимиты: 1 МБ в UI, до 500 правил. Повторный импорт создаёт отдельные копии.
Включённые правила после импорта работают как новые правила.
