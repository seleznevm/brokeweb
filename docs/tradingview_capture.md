# Как передать внутренние оценки и intrabar из TradingView

Обычная выгрузка графика в CSV — правильный способ получить исторические значения. Однако она содержит только опубликованные индикатором ряды, а не все его переменные. Подготовлены четыре диагностические копии **Scalping_SMA 1.15.2**. Они не предназначены для версии 1.16.5. Исходный файл 1.15.2 сохранён без изменений.

Из копий metrics/signals и contexts уже получены внешние CSV ETHFI 30m. Для актуальной копии intrabar **recorder v3 компиляция и исполнение на TradingView ещё не подтверждены**; она проверена локальным парсером проекта. Если Pine Editor покажет ошибку, передайте её текст, номер строки и имя копии: успешный разбор нашим парсером не заменяет проверку компилятором TradingView.

## Текущий шаг после pool-отчёта ad4e4 (2026-09-24)

Файл `TradingView_Alerts_Log_2026-09-24_ad4e4.csv` принят: **296 монет, TF30, 13 551 обновление**, 55 сессий с активными сетапами. Все пакеты — **recorder revision 2**, без синхронных request results. Запись охватывает только **01:24:43.861–01:27:12.007 UTC**, ни одна 30m-свеча не закрылась. Старый label `ETHFI-5m-20260922-01` не определяет символ или TF: импорт использует настоящую metadata каждой сессии.

Для следующей intrabar-записи:

1. Возьмите полный актуальный [файл регистратора](../tools/pine_reference/generated/Scalping_SMA_1.15.2_parity_intrabar.pine). Название теперь **PARITY intrabar v3**, короткое имя **SMA-P-R3**; это recorder для исходника **1.15.2**.
2. Сначала создайте новые alerts для 3–5 инструментов на обычном графике 30m с прежними defaults. Условие — **Any alert() function call**. Пример нового label: `pool-30m-v3-20260924`.
3. В первом JSON из Alerts Log убедитесь, что есть **`"recorder_revision":3`**, `request_routes`, `quote_currency`, `volume_type` и `dropped:0`. Если там revision 2, alert продолжает выполнять старую копию. TradingView сохраняет снимок скрипта и inputs при создании alert: [официальное объяснение](https://www.tradingview.com/pine-script-docs/faq/alerts/#if-i-change-my-script-does-my-alert-change). Одного обновления кода на графике недостаточно — alert нужно создать заново.
4. Записывайте **120 минут**, чтобы получить несколько закрытий 30m-свечей и полные переходы между ними. Экспортируйте весь журнал с начала запуска, не только последние строки. Потери `dropped` и пропуски пакетов нельзя восполнить историческим OHLCV.
5. Сохраните CSV под новым именем. Компиляция/исполнение recorder v3 на TradingView пока не подтверждены внешним capture; если редактор отклоняет код, нужны текст ошибки и номер строки.

Отдельно выявлена гипотеза о пустых барах: на 12 инструментах native-прогрев даёт расхождения ATR/EMA, а эксперимент без zero-volume bars совпадает. Для проверки нужен обычный CSV графика **BYBIT:EWTUSDT.P, 30m**, включающий минимум 1000 свечей перед **2026-09-24 01:00 UTC**, с OHLCV и PARITY metrics. CSV должен показывать реальные timestamps и volume; пропущенные интервалы не заполнять. Это проверка состава истории, а не повод уже сейчас менять production feed. [Подробный отчёт](parity.md#intrabar-pool-ad4e4-2026-09-24).

## Ранее выполненная выгрузка: время HTF и курс конвертации

В полученном `BYBIT_ETHFIUSDT.P, 30_caaff.csv` обнаружено расхождение времени появления часовых показателей. Также отношение объёмов после диагностического выравнивания постоянно внутри 175 из 184 UTC-дней. Чтобы выяснить причины, подготовлена [Scalping_SMA_1.15.2_parity_contexts.pine](../tools/pine_reference/generated/Scalping_SMA_1.15.2_parity_contexts.pine).

1. Откройте прежний обычный график **BYBIT:ETHFIUSDT.P, 30m**. Создайте новый личный индикатор, вставив **весь файл contexts**. Название на графике — `Scalping_SMA 1.15.2 - PARITY contexts`.
2. Оставьте на том же графике копию **PARITY metrics** и задайте одинаковые настройки в обеих копиях. Если лимит индикаторов мешает, signals для этой выгрузки можно убрать. Сообщите «настройки по умолчанию» либо перечислите изменения и внешние источники.
3. Перезагрузите страницу графика и дождитесь окончания вычислений. Загрузите историю, включающую хотя бы **10–20 сентября 2026**; желательно захватить также несколько более ранних дней. Так мы проверим и участки с непостоянным отношением объёмов.
4. Скачайте **новый CSV графика с данными индикаторов**, как в разделе 1. В нём должны быть `PARITY_CTX_return_1h_original`, `PARITY_CTX_return_1h_off`, `PARITY_CTX_return_1h_on`, `PARITY_CTX_quote_usd_requested`, `PARITY_CTX_quote_usd_used`, а также `PARITY_formation` из metrics.
5. Сохраните его под новым именем в `C:\dev\brokeweb\tradingview_data\full_reference\`, сохранив старую выгрузку. Сообщите имя файла и настройки. Alerts и intrabar-запись для этой проверки не требуются.

Contexts публикует 53 численных ряда: исходные часовые расчёты, начало/конец запрошенных свечей, сырой quote-volume и курс USD, HTF/MTF-значения, часть используемых настроек и metadata. Он содержит тот же детектор 1.15.2, а измерительные запросы добавлены после расчёта и не участвуют в сигналах.

Ряды с суффиксом `_on` намеренно показывают результат `lookahead_on` для распознавания причины сдвига. Они используют будущий результат часа на ранних исторических свечах, поэтому не пригодны для оценки сигналов или присвоения parity PASS. По [документации TradingView](https://www.tradingview.com/pine-script-docs/concepts/other-timeframes-and-data/#lookahead), исторический `lookahead_off` обновляется в конце периода HTF, а `lookahead_on` — в начале. Рабочий engine сохраняет `lookahead_off`.

## 1. Внутренние оценки: CSV графика

1. Откройте обычные свечи `BYBIT:ETHFIUSDT.P`, таймфрейм **30 минут**. Можно использовать другой инструмент из прежних выгрузок, но укажите его и таймфрейм. Не используйте Heikin Ashi, Renko или пересчитанный/составной символ.
2. В Pine Editor создайте два личных индикатора, полностью скопировав соответствующие файлы:
   - [Scalping_SMA_1.15.2_parity_metrics.pine](../tools/pine_reference/generated/Scalping_SMA_1.15.2_parity_metrics.pine) — 45 показателей, включая Formation, Execution, Geometry, Context, Exhaustion, MAE, AVG, Continuation, BTC Shock, уровни и состояния;
   - [Scalping_SMA_1.15.2_parity_signals.pine](../tools/pine_reference/generated/Scalping_SMA_1.15.2_parity_signals.pine) — 26 сигналов.
3. Сохраните и добавьте **оба индикатора на один график**. Их названия оканчиваются на `PARITY metrics` и `PARITY signals`. Если лимит тарифа мешает, освободите место на отдельном тестовом графике.
4. Установите одинаковые inputs в обеих копиях. Для первого прогона удобно оставить значения по умолчанию и написать «все настройки по умолчанию». При изменённых настройках приложите перечень изменений. Отдельно укажите выбранные источники `lazyExternalSource`, `oiExternalSource`, `cvdExternalSource`, особенно если это выходы другого индикатора.
5. Прокрутите график влево, чтобы загрузить нужную историю; дождитесь расчёта обоих индикаторов. Затем в верхнем меню графика выберите **Download chart data / Скачать данные графика**, включив данные индикаторов, если интерфейс предлагает такой выбор. CSV должен содержать колонки `PARITY_formation`, `PARITY_execution`, `PARITY_avg_setup` и остальные `PARITY_*`.
6. Сохраните один общий CSV в `C:\dev\brokeweb\tradingview_data\full_reference\`. Сообщите имя файла, символ, таймфрейм и настройки. Переписывать значения из таблицы вручную не нужно.

TradingView официально поддерживает [экспорт данных графика и индикаторов в CSV](https://www.tradingview.com/support/solutions/43000537255-how-to-export-chart-data/). Копии публикуют численные ряды через `plot(..., display.data_window)`; такие ряды доступны для экспорта согласно [описанию визуальных выходов Pine](https://www.tradingview.com/pine-script-docs/visuals/overview/). Отсутствие линий на самом графике ожидаемо.

Каждая копия также выводит шесть колонок `PARITY_META_metrics_*` или `PARITY_META_signals_*`: начало загруженной истории, индекс свечи, шаг цены, признак закрытия, объём и длительность таймфрейма. Разные префиксы позволяют экспортировать обе копии вместе. Сверка потребует совпадения истории и inputs; последнюю незакрытую свечу нельзя считать историческим reference.

Если тариф допускает только одну копию за раз, выгрузите два CSV с одинаковой историей и настройками, лучше после закрытия проверяемого диапазона. Отдельные выгрузки могут различаться текущей свечой; инструмент объединения отклоняет конфликтующие значения, а не выбирает одно из них.

## 2. Intrabar: CSV журнала оповещений

Intrabar-reference — последовательность вычислений индикатора **внутри ещё открытой свечи**. Обычный исторический CSV не позволяет восстановить её задним числом: Pine исполняется на обновлениях realtime-свечи, а исторические свечи содержат итоговые данные. См. [модель исполнения Pine](https://www.tradingview.com/pine-script-docs/language/execution-model/).

1. Создайте третий личный индикатор из [Scalping_SMA_1.15.2_parity_intrabar.pine](../tools/pine_reference/generated/Scalping_SMA_1.15.2_parity_intrabar.pine), сохраните и добавьте его на обычный график Bybit perpetual.
2. Для короткого первого сбора используйте `BYBIT:ETHFIUSDT.P`, **5 минут**, и оставьте запись на **15–20 минут**, чтобы получить несколько закрытий свечей. Для проверки прежнего таймфрейма 30 минут потребуется более длинная запись — примерно 60–90 минут.
3. Выставьте нужные inputs. В группе `PARITY capture` задайте уникальный `Capture label`, например `ETHFI-5m-20260921-01`.
4. Создайте новое оповещение. В поле условия выберите **Scalping_SMA 1.15.2 - PARITY intrabar v3**, затем **Any alert() function call / Любой вызов функции alert()**. Webhook, email и Telegram для этого способа не нужны. Лишние каналы уведомлений можно отключить.
5. Убедитесь, что в **Alerts Log / Журнале оповещений** появляются сообщения с началом `{"brokeweb_trace":1`. Первое сообщение отправляется при первом realtime-вычислении, следующие — при обновлении рынка не раньше чем через 20 секунд после предыдущего. При отсутствии обновлений отдельный таймер сообщение не отправляет.
6. После нескольких закрытых свечей дождитесь ещё одного сообщения журнала, затем остановите оповещение. В меню **журнала оповещений** выберите экспорт CSV. Нужен файл с полным текстом **Message / Сообщение**, а не повторная выгрузка графика.
7. Положите CSV в `C:\dev\brokeweb\tradingview_data\intrabar\` и сообщите имя файла. Не пересохраняйте сообщения через Excel: длинные JSON-строки должны остаться целыми.

TradingView подтверждает [экспорт Alerts Log в CSV](https://www.tradingview.com/support/solutions/43000691967-what-timezone-is-displayed-in-alerts/); время в этом экспорте — UTC. Импортёр использует миллисекундные timestamps внутри сообщений и не зависит от языка заголовков CSV или порядка строк.

Оповещение использует серверную копию скрипта и inputs на момент создания. После изменения кода, настроек, символа или таймфрейма создайте новое оповещение с новым capture label. Это поведение и ограничение частоты описаны в [FAQ TradingView об alerts](https://www.tradingview.com/pine-script-docs/faq/alerts/).

## Что записывается и какие есть ограничения

Каждое сообщение содержит пакет последовательных realtime-вычислений: OHLCV, 45 метрик, 26 сигналов в битовой маске, состояния свечи, порядковый номер обновления, источник Pine, символ, таймфрейм, начало истории и 298 inputs. Это вычисления Pine на потоке TradingView, а не обещание записать каждую биржевую сделку. Выбранные `input.source` и цвета автоматически не включаются; источники нужно указать отдельно.

Пакеты ограничены буфером 24 000 символов. При переполнении счётчик `dropped` явно отмечает потерянные вычисления. Сообщение длиннее 38 000 символов останавливает запись с ошибкой вместо отправки обрезанного reference. Это ниже [лимита alert()-сообщения 40 960 символов](https://www.tradingview.com/support/solutions/43000773947-alert-name-and-message-size-limits/). Интервал 20 секунд удерживает обычную отправку ниже ограничения 15 срабатываний за три минуты. Другие alert-вызовы исходного финального dispatch в диагностических копиях отсутствуют.

Импорт обнаруживает пропуски пакетов, переполнение, конфликтующие дубликаты, изменение metadata и неправильные значения. Совпадающие timestamps не склеиваются: два вычисления в одну миллисекунду сохраняются по `seq`. Начальная неполная свеча и неизвестный неотправленный хвост отмечаются явно. Отсутствие обнаруженных пропусков не доказывает, что запись охватывает всё нужное время.

Статус успешного импорта — `CAPTURE_IMPORTED`, а parity остаётся **UNVERIFIED**. Для сравнения нужны синхронизированный Python replay, такой же origin и внешние `request.*` контексты. Прямой запуск существующего comparator с `--realtime` на этом trace пока не является готовым процессом: его timestamp keys не различают несколько обновлений за одну миллисекунду. Импорт сохраняет такие данные для последующего сопоставления.

Pine Logs можно использовать для небольших ручных диагностик, но здесь предусмотрен документированный CSV-экспорт Alerts Log. Скриншот таблицы годится для отдельных значений, однако не заменяет intrabar-последовательность. Поднимать публичный webhook или открывать доступ к локальному Docker не требуется.

## Локальные команды для разработчика

Запускать из корня проекта; пользователь может просто положить файлы в указанные каталоги.

```bash
python3 -m tools.pine_reference.exporter

# Для двух раздельных CSV; общий CSV повторно объединять не требуется:
python3 -m tools.pine_reference.merge metrics.csv signals.csv --output artifacts/local/reference.csv

# Для журнала оповещений; каждый запуск пишет в новый каталог:
python3 -m tools.pine_reference.trace \
  --input tradingview_data/intrabar/alerts.csv \
  --output-dir artifacts/local/intrabar-import-001
```

Для каждой сессии создаются `reference.jsonl`, `metadata.json`, `report.json`. Существующие файлы сессий не перезаписываются. Повреждённый вход возвращает exit code 2; успешный импорт возвращает 0, даже если отчёт обнаружил пропуски — это успех импорта, не подтверждение полноты.

## Полученный intrabar-журнал 2026-09-22

`TradingView_Alerts_Log_2026-09-22_0c635.csv` обработан: 48 пакетов, 253 обновления ETHFIUSDT.P **5m** за 04:20:39–04:39:21 UTC. Пропусков последовательности и переполнения нет; три разные свечи закрылись, две записаны от первого обновления до закрытия. Последняя свеча открыта, неотправленный хвост неизвестен. Все 298 переданных inputs соответствуют defaults; источники plot и цвета протокол не передаёт.

Исправлена ошибка строкового encoder в регистраторе: прежняя обработка `\r` заменяла букву `r`. Pine поддерживает только перечисленные [escape sequences](https://www.tradingview.com/pine-script-docs/concepts/strings/#escape-sequences). Import восстановил два однозначных enum-значения (`Proxy TradingView`, `Normal`), сохранив исходные значения и запись исправлений. CSV и численные наблюдения не менялись; повторять эту запись из-за ошибки не требуется.

Для исправления encoder была выпущена копия `PARITY intrabar` с `recorder_revision=2`. Последующая запись da14b подтвердила её работу. Актуальная версия регистратора описана ниже.

ATR/EMA20/EMA50 прошли ограниченную сверку всех 253 обновлений с прогревом по 20 500 native свечам. [Отчёт](../reports/intrabar-capture.json) сохраняет общий intrabar-статус **UNVERIFIED**: активных сетапов и сигналов в этой сессии нет; протокол пока не записывает синхронные внешние `request.*` контексты. Более длинная запись сама по себе не устраняет это ограничение — для полной сверки нужно дополнить регистратор и replay контекстами и затем проверить участок с активными сетапами.

Ограниченная сверка ATR/EMA:

```bash
python3 -m tools.pine_reference.trace_prices \
  --input 'tradingview_data/intrabar/TradingView_Alerts_Log_2026-09-22_0c635.csv' \
  --cached-fixture artifacts/local/contexts-ethfi/fixture.json \
  --output-dir artifacts/local/intrabar-price-check-002
```

Каталог должен быть новым. Команда сохраняет native warmup, Python observations и отдельный отчёт с SHA-256 входов; исторический parity-отчёт не заменяет. Одинаковые timestamps и повторные closing executions сохраняются по `seq`, а история ATR/EMA фиксируется один раз на свечу.

### Recorder revision 3: синхронные результаты request.*

Актуальная сгенерированная копия `Scalping_SMA_1.15.2_parity_intrabar.pine` дополняет каждую строку результатами всех десяти исходных запросов: часовые activity-метрики, курс quote→USD (включая `null`, когда rate недоступен), четыре MTF tuple, HTF base, семь lower-TF массивов, BTC regime и BTC Shock. Это данные на границе запросов: они предназначены для проверки последующих вычислений на графике. Подстановка этих результатов сама по себе не проверяет вычисления **внутри** `request.*` по native OHLCV. Исторический прогрев, начальное persistent/varip-состояние и привязки внешних `input.source` остаются отдельными условиями полной сверки. Диагностический replay для revision 3 описан ниже; полной сверки пока нет. Сам импорт сохраняет `UNVERIFIED` и `comparison_ready=false`.

Импорт revisions 1/2 остаётся совместимым. Старым CSV контексты не дорисовываются. Revision 3 требует все поля и одинаковую длину семи lower-TF массивов; пустые массивы сохраняются как пустые. Для будущей записи потребуется обновить код и пересоздать alert с новым label. Revision 3 сгенерирована и проверена локальными тестами; компиляция и исполнение именно этой версии на TradingView ещё не подтверждены. Предыдущие CSV и их результаты ATR/EMA остаются действительными.

### Диагностический replay recorder v3

```bash
python3 -m tools.pine_reference.trace_replay \
  --input tradingview_data/intrabar/alerts-v3.csv \
  --warmup-fixture artifacts/local/capture-warmup.json \
  --output-dir artifacts/local/intrabar-context-replay-001
```

Команда работает офлайн. Warmup fixture использует формат обычного `tools.pine_reference.replay`: `symbol` без `.P`, `timeframe`, `tick_size`, `parameters`, `bars`, `contexts`, опционально `currency_rates`. Chart bars должны быть закрытыми, без пропусков и покрывать **ровно** участок от записанного `history_start` до начала первой записанной свечи; не следует включать саму эту свечу. Символ/TF/tick и все переданные recorder inputs должны совпадать. Контекстные потоки хранят native OHLCV под ключами `EXCHANGE:SYMBOL.P|TF`. Валютные наблюдения для прогрева задаются обычным ограниченным по времени форматом fixture. Начальное состояние вычисляется по этой истории; его совпадение с TradingView пока не доказано.

Затем исходный Pine AST выполняется для каждого записанного `seq`. Только исходные `request.*` вызовы получают наблюдения recorder; формулы, gates, FSM и сигналы вычисляются исходным детектором. Маршрут запроса проверяется при каждом вызове; контексты разных вызовов не смешиваются даже при одинаковом TF. Массивы копируются, чтобы выполнение не меняло reference. `barstate.isnew` берётся из записи, включая старт внутри открытой свечи. Повторные confirmed-executions сохраняются по порядку, а последнее состояние закрытой свечи фиксируется один раз при переходе к следующей. Эта модель повторных закрытий ещё требует проверки на TradingView. Последний бар не фиксируется; возобновляемый checkpoint команда не экспортирует.

Stateful replay требует seq=1, непрерывной последовательности без `dropped`, полных request-наблюдений и корректных переходов между свечами. Старые v1/v2 отклоняются. Начало внутри свечи допускается только с первого выполнения recorder; неизвестные предыдущие live-вычисления не реконструируются, поэтому начальное `varip`-состояние остаётся ограничением. Сейчас native warmup поддерживает только base volume / USDT quote; включённые внешние OI/CVD/LazyScalp plot также отклоняются, поскольку их bindings не записаны.

Результаты — `python.jsonl` и `report.json` с SHA-256 обоих входных файлов, 45 метриками, 26 сигналами, первыми расхождениями по `seq` и статистикой отсутствующих warmup-контекстов. OHLC и непосредственно подставленные request-метрики помечаются `SUPPLIED_INPUT_CHECK`; остальные — `DOWNSTREAM_CALCULATION`. Сигналы содержат TP/FP/FN/TN, отсутствие положительных событий отмечается отдельно. Численные допуски этой диагностики: точное совпадение discrete/bool и сигналов, `tick × 1e-8` для OHLC, один tick для price, относительная ошибка 0.0005 для indicator, абсолютная 0.05 для score. Это отдельная диагностика, а не критерии прежнего исторического acceptance-отчёта.

Статусы — `DIAGNOSTIC_MATCH` (exit 0), `DIAGNOSTIC_MISMATCH` (exit 1) или `INVALID_INPUT` (exit 2). Даже при полном диагностическом совпадении `parity_status` и `full_intrabar_status` остаются **UNVERIFIED**. Каталог результатов должен быть новым. Внешней записи v3 для проверки этого replay пока нет; локальные синтетические тесты проверяют реализацию и не заменяют её.
